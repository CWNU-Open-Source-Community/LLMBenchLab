# LLMBenchLab 项目章程

- 文档状态：Active
- 面向版本：MVP（Phase 0–1）
- 当前定位：个人开发者与研究人员使用的本地优先 LLM 能力评测平台

## 背景

个人开发者经常需要比较不同 LLM、不同服务端点和不同生成参数，但临时脚本难以保存完整配置，厂商页面的指标也通常无法复现个人数据集上的结果。模型输出解析、失败请求、Token 与成本统计若缺少统一协议，排行榜会产生误导。

LLMBenchLab 以一个可在单机运行的完整垂直切片解决这些基础问题：用版本化 Benchmark 驱动评测，通过统一 Adapter 调用模型，通过确定性的 Evaluator 评分，并保存从原始回答到汇总指标的证据链。

## 问题定义

项目要解决的核心问题是：如何让个人用户以较低部署成本，重复执行一组定义明确的客观题评测，并可信地回答“哪个模型在何种数据、协议与配置下表现如何”。

当前常见痛点包括：

- 模型接入方式和参数散落在脚本中，难以复用。
- 数据版本、Prompt、评分器及错误处理不透明，结果不可复现。
- 请求失败被忽略，导致只统计成功回答时分数虚高。
- 原始输出、解析结果、延迟、Token 和成本没有统一保存。
- 本地实验缺少可浏览的进度、逐题证据与可比排行榜。

## 产品愿景

成为一个轻量、透明、可扩展的个人 LLM Benchmark 实验台：用户可以在几分钟内用完全离线的 Mock 流程验证安装，再以同一协议接入 OpenAI-compatible 服务和自定义 Benchmark；任何成绩都能追溯到数据 Hash、协议版本、模型参数和逐题响应。

## 目标用户

1. **个人开发者**：验证候选模型或推理服务是否适合自己的应用。
2. **LLM/应用研究人员**：管理小规模可复现实验和自定义客观数据集。
3. **开源贡献者**：新增 Adapter、Evaluator、数据格式或界面能力，并通过离线 CI 验证。

MVP 不面向需要组织级权限、海量并发、合规托管或公网多租户服务的团队。

## 核心价值

- **可复现**：冻结 Benchmark 版本与 Hash、协议、Prompt、生成参数、模型信息和 Git SHA。
- **诚实计分**：失败题计入严格总分，同时展示完成率和已回答准确率。
- **证据可查**：保留逐题原始输出、解析答案、标准答案快照、评分和错误。
- **低门槛**：SQLite、本地进程内任务与 Mock 模型形成无需外部服务的默认路径。
- **可扩展**：Adapter、Evaluator、Runner 和 Dataset Loader 各自有清晰接口，未来可替换 Worker 或增加评测类型。
- **安全默认**：只保存密钥环境变量名称；CI 和演示不访问真实付费 API。

## 项目目标

### Phase 0–1 目标

- 建立治理、需求、架构、协议、ADR、状态、阶段和工作日志体系。
- 完成“注册 Mock 模型 → 载入 Demo → 创建 Run → 后台逐题生成与评分 → 保存 → 查看进度/结果/排行榜”的离线链路。
- 支持 `mock` 和 `openai_compatible` 两种模型配置，以及 exact match、multiple choice、numeric 三类客观评分。
- 提供本地启动、可选 Docker Compose、自动化测试和只使用 Mock 的 CI。

### 成功指标

| 指标 | MVP 成功标准 |
|---|---|
| 离线可用性 | Smoke Test 无网络、无 API Key 完成完整 Run |
| 链路完整性 | 每个计划题目产生 Response 或可解释错误，Run 进入终态 |
| 复现信息 | 已完成 Run 保存协议、数据 Hash、Prompt、生成参数、模型和运行时快照 |
| 评分透明度 | 同时提供严格总分、`answered_accuracy`、`completion_rate` 及逐题证据 |
| 工程质量 | 后端测试/lint、前端测试/lint/typecheck/build 和 CI 配置可执行 |
| 安全基线 | 仓库和 API 不含真实密钥，自动化不访问真实模型 |
| 可维护性 | Phase、ADR、状态、日志和下一任务文档与实现一致 |

成功标准评价产品与工程能力，不以 Demo 分数作为任何模型能力结论。

## 非目标

MVP 不实现或不承诺：

- 下载或分发完整 MMLU、GPQA、HumanEval 等大型公开数据集。
- 执行不可信代码或提供代码评测沙箱。
- LLM-as-a-Judge、Pairwise Judge、人类 Arena、Agent/Tool Use 和长上下文评测。
- 多用户、鉴权授权、支付、租户隔离或面向公网的生产托管。
- Kubernetes、微服务、Redis、分布式 Worker 或高可用调度。
- 模型服务质量保证、统计显著性结论或“通用智能”排名。

上述能力只能进入 Roadmap，不能增加 MVP 关键路径复杂度。

## 项目边界

### 范围内

- 单仓库、前后端分离的 Web 应用；FastAPI/SQLAlchemy/SQLite 后端和 React/TypeScript 前端。
- 版本化 JSON manifest + JSONL 数据集导入、验证和稳定 SHA-256。
- 本地 Mock 及用户配置的 OpenAI-compatible Chat Completions 接口。
- 进程内、受控并发、可取消标志的后台 Run；逐题隔离错误并持久化状态。
- 客观、确定性的 Evaluator 与可筛选排行榜。
- 面向开源协作的测试、CI、License、贡献和变更记录。

### 范围外与责任边界

- 用户负责确认外部模型和数据集的许可、费用、隐私与使用条款。
- 项目不自动上传数据；只有用户显式配置 OpenAI-compatible 模型时，Prompt 才会发送到其指定端点。
- 自定义 `base_url` 在 MVP 中属于受信配置；其 SSRF 风险使本项目不适合直接暴露公网。
- 进程内后台任务在进程重启后不能自动恢复；遗留 `running` Run 应标记为失败或中断并说明原因。
- SQLite 面向本地低并发使用，不承诺多进程写入吞吐与高可用。

## 指导原则

1. 结果可追溯优先于展示效果。
2. 严格且可解释的客观评分优先于模糊匹配。
3. 默认离线、安全、低成本；真实模型接入必须由用户显式配置。
4. 先完成可靠垂直切片，再按 Roadmap 替换基础设施。
5. 项目状态以测试和验收证据为准，不以文件存在或计划完成为准。
